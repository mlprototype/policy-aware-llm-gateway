# AWS Cost Optimization & Deployment Strategy

本ドキュメントでは、`Policy-Aware Multi-LLM Gateway` をAWS環境へデプロイ・運用するにあたってのコスト管理方針（Cost-Aware Architecture）およびTerraformによるインフレ設計思想について説明します。

---

## 1. 背景と設計方針：本番想定構成 vs 個人開発検証構成

本システムは、エンタープライズ環境での本番運用を想定し、**ECS Fargate、ALB、RDS PostgreSQL、ElastiCache Redis、AWS Secrets Manager、Amazon Bedrock** などを組み合わせた可用性の高いマルチアベイラビリティゾーン構成を理想としています。

しかし、これらすべてのリソースを検証環境で常時起動した場合、固定費の大部分を占めるNAT GatewayやALB、データベース等の基本料金により、月額約100〜150ドル以上のコストが定常的に発生します。

そこで本プロジェクトでは、**「完全にコストゼロを目指すのではなく、セキュリティや運用上不可欠なコア要素（Secrets Manager等）は実運用基準で導入しつつ、高コストなインフラ構成要素（NAT Gatewayや常時稼働ALB等）をオンデマンド化して無駄なアイドルコストを排除する」** という、実務的でバランスの取れたコスト最適化設計（Cost-Aware Architecture）を採用しています。

### コスト削減とセキュリティを両立する主要な設計決定
1. **常時非稼働ポリシー（Zero-Idle Running）の徹底**: ECSのコンテナ起動数を制御
2. **主要な有料コンポーネントのオプショナル（トグル）化**: ALB、RDS、Redisをオンデマンドで作成可能にする
3. **既存のネットワークインフラの再利用**: NAT Gatewayを排除し、パブリックサブネットを流用
4. **AWS Secrets Manager によるセキュアな認証情報管理**: わずかな固定費（シークレットあたり月額 $0.40）で、本番品質のシークレット管理を検証
5. **CloudWatch Logsの短期保持と標準メトリクスによるダッシュボード監視**
6. **ECR ライフサイクルポリシーによるストレージ最適化**
7. **GitHub Actionsの実行時間短縮と非同期デプロイプロセス**
8. **検証後のリソース選別破棄（Selective Cleanup）**

---

## 2. コスト抑制と実運用設計の詳細

### 2.1 ECSタスクのオンデマンド起動 (`desired_count = 0`)
ECS Fargateの課金は、タスクが実行されている時間（秒単位）に対してのみ発生します。
- **設計**: Terraformの変数 `desired_count` のデフォルト値を `0` に設定。
- **運用**: 開発・検証は基本的にローカルの `docker compose` で実施し、AWS上での結合検証を行う時だけ `desired_count = 1` にスケールアウトします。検証完了後は即座に `0` に戻すことで、無駄なコンテナ稼働費を排除します。

#### Redis未起動時におけるアプリケーションの自律起動とFail-open設計
本システムは、Redisが一時的に停止している、あるいはRedisがプロビジョニングされていないインフラ最小構成状態であっても正常に起動します。
- **プロファイルの分離 (`aws` プロファイル)**:
  ローカルの検証（Docker Compose等）では `local` プロファイルを使用し、AWS上のECSタスクでは専用の `aws` プロファイル（`SPRING_PROFILES_ACTIVE=aws`）を有効化するように設計しています。これにより、環境特有のDB/Redis接続情報やログ構成を `application-aws.yml` に完全に分離カプセル化しています。
- **遅延初期化**: Spring Boot（Lettuce）のRedis接続は遅延初期化されるため、起動時にRedisとの接続確認が走ってコンテナがクラッシュすることはありません。
- **主要フローの継続性**: RedisはRate Limit用途のみで使用され、接続失敗時は自動的に例外を捕捉して `UNAVAILABLE` ステータスを返し、処理を通過（Fail-open）させる設計になっています。これにより、Redisの停止を理由に認証、コンテンツセキュリティ、LLMルーティングといったGatewayのコアフローが過剰に停止しないよう耐障害性が確保されています。

### 2.2 有料リソースのオプショナル作成（フィーチャートグル）
ALB、RDS PostgreSQL、ElastiCache Redis は、Terraformの `count` パラメータを用いてデフォルトで「作成しない」設定にします。
- **`enable_alb = false` (デフォルト)**:
  検証時はECSタスクにPublic IPを直接割り当てて直接APIを叩くことで、ALBの固定費（約20ドル/月）を削減します。
- **`enable_rds = false` / `enable_redis = false` (デフォルト)**:
  モック検証や簡易稼働確認時は不要とし、本番相当の連携テストを行う場合のみ一時的に有効化します。

### 2.3 NAT Gatewayの排除とPublicサブネット配置
本番環境ではタスクをPrivateサブネットに配置し、NAT Gateway経由で外部LLM API（OpenAI, Anthropic）へアウトバウンド接続するのが定石ですが、NAT Gatewayは稼働しているだけで約32ドル/月のコストがかかります。
- **設計**: 初期MVPおよび個人検証構成ではNAT Gatewayを作成せず、ECSタスクをPublicサブネットに配置してPublic IPを付与します。
- **結果**: 外部APIへのアウトバウンド通信をNAT Gatewayなしで直接実行可能にし、固定費を完全に排除します。

> [!WARNING]
> **本番環境への移行についての重要な注意点**
> この「Public Subnet + Public IP」による直接配置構成は、**個人開発における短時間の疎通確認用途に限定**されます。本番環境では、セキュリティ確保のためにECS Taskを必ずPrivate Subnet上に隠蔽してALB経由で公開し、外部APIへの通信はNAT GatewayまたはVPC Endpoint（Amazon Bedrock等とのプライベート通信用）を経由する構成を適用する必要があります。

### 2.4 AWS Secrets Manager による本番基準の鍵管理
APIキー（OpenAI / Anthropic）やデータベースの認証情報などの機密情報を環境変数にハードコードしたり、Gitにコミットしたりすることは、実運用ではセキュリティ上許容されません。
- **設計**: 本プロジェクトでは、シークレット管理サービスである **AWS Secrets Manager** をデフォルトでインフラ構成に組み込みます。
- **コストと設計の最適化（JSONによる単一シークレット化）**:
  Secrets Managerは **シークレット1つあたり月額 $0.40** の基本料金が発生します。
  - **個人開発における最適化**: 固定費を極小化するため、複数のProvider API Key（OpenAI, Anthropic 等）やDBの接続情報を、**1つのJSONオブジェクト形式のSecret** にまとめて格納するアプローチを採用します。これにより、Secrets Managerの課金を月額 $0.40（1シークレット分）のみに抑えつつ、安全な鍵管理機構を構築します。
  - **本番環境での設計**: 一方で、本番環境では各キーに対するIAMポリシーでの最小権限制御（権限分離）や、個別キーの自動ローテーション周期を考慮し、用途ごとに個別のSecretに分割して管理する設計を検討します。

### 2.5 CloudWatch Logsの短期保持とダッシュボード構成の最適化
- **ログ短期保持**: デフォルトでは蓄積され続けるログのストレージコストを防ぐため、ログの保持期間を **1日** に制限します。個人開発の検証ログはリアルタイムまたは翌日確認できれば十分であるため、長期保管コストをカットします。
- **ダッシュボードの簡素化**: CloudWatchカスタムダッシュボードを作成するにあたり、追加コストを発生させないためダッシュボードの数を制限（無料枠でカバーされる3つ以内のルールを適用）し、追加課金が発生する「カスタムメトリクス」や「Container Insights」は無効化します。AWS標準で提供されるECSのCPU/Memory使用率やタスク起動数メトリクスのみをグラフィカルに集約します。

### 2.6 ECR ライフサイクルポリシーによる最新イメージの制限
DockerイメージをビルドしてECRにプッシュし続けると、古いイメージがストレージを圧迫し課金が発生します。
- **設計**: ECRリポジトリにライフサイクルルールを適用し、**「最新の3イメージのみを保持し、古いイメージは自動削除」** するように構成します。

### 2.7 GitHub Actionsの実行時間最適化と非同期デプロイ
GitHub Actionsはプライベートリポジトリの場合でも月2,000分の無料ビルド時間が提供されますが、不要なデプロイ待ちによるランナーの占有を防ぎます。
- **キャッシュの最大活用**: Gradle의 ビルドキャッシュとDockerのレイヤーキャッシュ（`gha` キャッシュバックエンド）を活用し、ビルド時間を1回あたり2〜3分以内に短縮します。
- **非同期ECSデプロイ**: `aws-actions/amazon-ecs-deploy-task-definition` の `wait-for-service-stability` オプションを `false` に設定します。`desired_count = 0` の状態ではデプロイの「コンテナ起動完了（スタビリティ）」を待つとタイムアウトまでランナーが走り続け、無料枠を浪費するため、タスク定義の更新登録が成功した時点でワークフローを即時正常終了させます。

### 2.8 検証後のリソースクリーンアップポリシー（選別破棄）
検証終了後に `terraform destroy` を実行する際、機械的にすべてを削除してしまうと、イメージ格納用のECRやTerraformのState情報、IAM Roleの再作成に無駄な時間がかかってしまいます。そのため、実務に即して「検証後に削除すべき高コストな動的リソース」と「維持し続けるべき低コストまたは静的なリソース」を以下のように分類し、トグル変数や個別のコマンドで選別して破棄します。

#### 検証後に削除すべき（一時的・高コストな）リソース
以下のリソースは稼働時間ベースで課金が発生、または攻撃対象となるため、検証完了後に即時削除します（変数を `false` または `0` に変更して `terraform apply` するか、個別に `destroy` します）。
- **ALB (Application Load Balancer)**: 稼働固定費の発生防止
- **ECS Service / running task**: `desired_count = 0` に変更し、コンテナを完全に停止
- **RDS (PostgreSQL)**: DBインスタンスの削除
- **ElastiCache (Redis)**: Redisクラスターの削除
- **NAT Gateway (導入した場合)**: ネットワーク固定費の発生防止
- **一時的なSecurity Group**: 不要なインバウンドポートのクローズ

#### 必要に応じて維持する（低コスト・永続的な）リソース
以下のリソースは、保持していても極めて低コストであり、次回以降の検証時間を短縮し再現性を高めるために、そのまま残すことを推奨します。
- **ECR Repository**: すでにプッシュしたコンテナイメージの再ビルドを避けるため（ライフサイクルポリシーにより容量はクランプ済）
- **CloudWatch Log Group**: 1日保持の設定により自動的に肥大化が抑えられるため
- **Terraform State**: インフラ構成の追跡と整合性を保つためのtfstate（S3やローカルなど）
- **IAM Role / Policy**: 作成時の固定費が発生せず、認証ポリシーの記述を維持するため

## 4. 設計における技術的妥協点と本番への移行パス

低コスト化を実現するにあたり、以下の技術的トレードオフを許容しています。これらは本番環境へ移行する際にポリシーを変更するだけでスケール可能です。

1. **データベース接続のフォールバック**
   - `enable_rds = false` の場合、AWS上のECSタスクは正常に起動できません（Spring Boot起動時にPostgreSQL接続が必須なため）。
   - **ガードレール設計**: 誤った設定（`desired_count > 0` かつ `enable_rds = false`）のまま適用してクラッシュループに陥るのを未然に防ぐため、Terraformの **`lifecycle.precondition`** 機能を利用して `plan` 時に自動的に検出してブロック（デプロイ拒否）するガードを定義しています。
   - **対策**: 結合検証を行う場合は必ず `enable_rds = true` に設定してRDSを一時的に同時にプロビジョニングし、検証完了後に再度両方を `false`/`0` に戻す運用とします。
2. **セキュリティグループによる直接アクセスの保護**
   - ALBを利用しない場合、ECSタスクに直接パブリックアクセスすることになります。
   - **対策**: タスクのSecurity Groupにおいて、`allowed_ingress_cidr` を検証元マシンのグローバルIP（`/32`）に制限し、パブリック全体にポートを開放しないように設計します。
